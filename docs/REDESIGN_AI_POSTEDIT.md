# VoxCraft 再設計案 — 認識で当てにいくのをやめる

作成: 2026-08-28 / 更新: 2026-08-28 / 対象: `0.23.0` 以降 / 種別: 仕様（方針決定済み・計測待ち）

仕様と機能をもう一度一から検討した結果をまとめる。結論・その理由・**捨てるものの一覧**まで書く。

**決定済み（2026-08-28）**: ローカルLLMは実測してから判断する。口述は
「原稿執筆モード」（フィラー除去・整形あり）と「対話モード」（表記の訂正のみ）に分け、
**まず原稿執筆モードだけ作る**。降格する対話機構は実測の結果を見てから決める。
取材ノートは**生テキストが正式**で、表記だけは直す。

門と計測の道具は実装済み（§12）。残っているのは、実際にモデルを立てて測ること。

---

## 1. 診断 — なぜ満足に届かないのか

現行には、明文化されていない前提が2つある。

1. 認識結果が本文に落ちた時点で、ほぼ正しい。
2. 残った誤りは**1件ずつ、その場で、対話的に**直す。

0.10 から 0.23 までの開発は、ほぼ全部この2番めを強くする作業だった。再変換、読みの揺らし、
叩いて直す、範囲を広げる、言い直し、辞書のクイック登録、ノートへの辞書適用。
どれも良くできているが、前提そのものに4つの限界がある。

### 1-1. 修理コストが誤り1件ごとに掛かり、思考を中断する

READMEには「**誤変換・誤認識を直す（どれを使うか）**」という表がある。利用者は誤りを見つけた
うえで、さらに「読みは合っているか」「読みごと壊れているか」「英字か」を**分類してから**
道具を選ぶ。これは認識器の内部事情がそのまま操作に出ている状態で、口述の目的（考えを止めずに
書く）と正面から衝突する。1件あたり数秒でも、文章を書く速度を決めているのは操作時間ではなく
**中断の回数**のほう。

### 1-2. 認識の天井は、対話では破れない

0.20.3 で自分たちで測ったとおり。

> 読みは どうおんい**き**ご で、正しい どうおんい**ぎ**ご とは濁点1つ違い。濁点の有無は音として
> 小さく、モデルの言語的な事前分布のほうが強い。**同じ言葉をはっきり言い直しても結果は動かない**。

ここが本質。**音をもう一度入れても越えられない壁**があり、それを越えるのに要るのは
より良いマイクでも大きいモデルでもなく、**前後の文脈を持った別の判断**である。
現行はその判断を全部「人間の目と指」に割り当てている。

### 1-3. 辞書は片方向のラチェットで、しかも破壊的

辞書は無条件置換なので、危ないのは**誤りを直すつもりで正しい語を潰す**登録だった
（0.23.0：「マイナカード」を登録すると本文の「マイナンバーカード」29箇所が消える）。
そのためにプレビュー機構・省略判定・件数の数え方まで作り込んだ。よく効いているが、
**事故を防ぐ機構が必要になる時点で、道具の形が用途に合っていない**。
「この語はこの分野ではこう書く」は本来、文脈を見て適用する知識であって、全文一括置換ではない。

### 1-4. 正しく認識できても、話し言葉は文章ではない

ここが、たぶん「満足いかない」の最大の成分。

フィラー（えー、あの）、言い直し（〜じゃなくて〜）、助詞の崩れ、係り受けの飛び、
文の切れ目の曖昧さ、段落なし。**認識精度が100%でも残る**問題で、現行はここにほとんど
何も持っていない。句読点は形態素ルール（README自ら「Google日本語入力ほどの精度ではない」）、
段落は文字数と間の閾値。見出し・箇条書き・話者ラベルは無い。

つまり現行は「認識精度」の問題を解き続けてきたが、**残っている不満の大半は
「認識のあとの工程が存在しない」ことに由来する**。

## 2. 設計原理の入れ替え

一行で書く。

> **音は音でしか決まらないことだけ決めさせ、文脈が要る判断は文脈を持つモデルへ渡す。**

判断ごとに、必要な情報と担当を置き直すと、現行のねじれが見える。

| 判断 | 決めるのに要る情報 | 現行の担当 | 新しい担当 |
|---|---|---|---|
| 音素・語彙の書き起こし | 音声 | Whisper | **Whisper（変えない）** |
| 同音異義語の選択 | 前後の文脈・話題 | 人（叩く→候補→選ぶ） | **AI校正** |
| 固有名詞・専門用語の表記 | 分野知識・用語集 | 辞書（無条件置換） | **AI校正**（用語集を事前分布として） |
| 句読点 | 統語 | 形態素ルール | **AI校正** |
| 段落・見出し・箇条書き | 談話構造 | 文字数と間 | **AI整形** |
| フィラー・言い直しの整理 | 話者の意図 | なし（人手） | **AI校正**（口述モードのみ） |
| 読みごと壊れた誤認識 | **新しい音** | 言い直し | **言い直し（残す）** |

最後の行が要点。**AIで置き換えられない対話機能はこれ1つだけ**である。音に入っていない情報は
どんなモデルでも復元できないので、そこだけは人がもう一度喋るしかない。逆に言えば、
それ以外の対話機構は、原理的にAI側へ寄せられる。

利用者から見た変化は、機能の増加ではなく**覚えることの減少**になる。

- 誤りの種類を分類しなくていい（道具の選択表が要らない）。
- 誤りを見つけるために手を止めなくていい（見つける前に直っている）。
- 辞書を育てなくても、今日のノートがその日のうちに読める。

## 3. モードは3つ。分ける軸は忠実性の要否

現行は口述と文字起こしを1つの後処理で扱っている。ここを**3つに分ける**。
軸は速度でも遅延でもなく、**話したとおりであることがどれだけ要るか**。

| | 原稿執筆 | 対話 | 取材 |
|---|---|---|---|
| 使う場面 | 自分の文章を口述する | 話したまま残したい口述 | 他人の発話・引用が要る |
| 著者 | 自分 | 自分 | 話した本人 |
| 同音異義・固有名詞の訂正 | ○ | ○ | ○ |
| 句読点 | ○ | ○ | ○ |
| フィラー除去 | **積極的に** | 抑えめ（明らかなものだけ） | **しない** |
| 文体の整え | ○ | ✕ | ✕ |
| 言い換え・要約 | ✕ | ✕ | ✕ |
| 正となるテキスト | 校正稿 | 校正稿 | **生テキスト** |
| 実装 | **まず作る** | 後（コスト次第） | 作る（門は既にある） |

**まず原稿執筆モードだけ作る。** 対話モードは、原稿執筆で実際にどれだけ効くか・
どれだけ掛かるかを見てから足す。門（`refine_guard.CONVERSATION`）は先に置いてあるので、
プロンプトを1つ足せば動く状態にしてある。

**取材ノートは生テキストが正式。** そのうえで表記だけは直す。この2つは両立する ——
取材モードの校正は読みを変えないので、**生テキストと校正稿は同じことを言っている**
ことが機械で保証される（§5-1）。引用の検証は音と生テキストで行い、読むのは校正稿でよい。

ここで実測してひとつ分かったことがある。**原稿執筆モードの出力を取材モードの門に
掛けると、全ブロックが落ちる。** フィラーを消した時点で読みが変わるためで、これは
正しい挙動。裏を返すと、**取材ノートに掛けるときは取材モードのプロンプトで走らせる
必要がある**（原稿執筆モードで走らせて門で止める、では何も直らない）。

## 4. 新しいパイプライン

```
  音声
   │
   ├─ Stage 0  取り込み        VAD / ノイズ減算 / 連結 / 言語判定      ← 据え置き
   │
   ├─ Stage 1  認識            Whisper → 生テキスト(raw)              ← 据え置き
   │                            ★ raw は音声と対で永久に残す
   │
   ├─ Stage 2  決定的後処理     和欧スペース / 記号語 / 明示コマンド    ← 縮小
   │                            / 曖昧さのない綴り置換のみ
   │
   ├─ Stage 3  AI校正 (新)      同音異義・固有名詞・句読点
   │                            (口述のみ) フィラー・言い直しの整理
   │                            → 検証 → 差分 → 差し替え
   │
   └─ Stage 4  AI整形 (新・任意) 段落 / 見出し / 箇条書き / 話者ラベル
```

**Stage 0 は触らない。** 実測で最適点に置いてあり（連結10秒、減算の強さをSNRで決める、
言語判定は base + 確信度0.75）、この提案はそこを一切変えない。

**Stage 2 を縮小する。** 今そこにある2つを外へ出す。

- **辞書の無条件置換** → 曖昧さのないもの（`SMTV`→`SMTB` のような綴りの誤り）だけ残す。
  読みとして曖昧なキーは Stage 3 の用語集へ移す。分ける基準は「キーが読みとして一意か」。
- **形態素ルールの自動句読点** → Stage 3 がある時は不要。ただし AI校正が落ちた／却下された
  ときのフォールバックとして残す（削除しない）。

**契約（重要）**

- Stage 1 の出力は不変。Stage 3 以降は**必ず raw から再計算できる**。
  → プロンプトやモデルを変えたら、保存済み録音に対して**認識をやり直さずに**
    校正だけ回し直せる（`retranscribe.py` の思想を、後段だけに適用する）。
- Stage 3/4 は**べき等**。同じ raw ＋同じ用語集＋同じモデルなら同じ結果に落ちる
  （温度0、決め打ちの分割）。
- Stage 3/4 が触ってよいのは、**口述範囲として記録されている箇所だけ**
  （`plugin/dictated.ts` が既に持っている。手で書き換えた箇所は範囲から自動的に外れる）。

## 5. AI校正の安全性仕様 — この提案の核心

プロンプトに「勝手に書き換えるな」と書くのは仕様ではない。**機械で落とせる不変条件**を置く。
`server/refine_guard.py` に実装済み（`server/test_refine_guard.py`、21件）。

### 貫いている規則はひとつ

> **消す方向は通し、作る方向は通さない。**

校正・言い換え・要約・幻覚のどれであっても、危ないのは「音に無かったものが本文に
現れること」だけ。落ちたぶんは欠落の門が別に見る。だから読みも数値も固有名詞も、
**等しさではなく包含で判定する**。「一つ」→「ひとつ」で数値が消えるのは事故ではない。

### 5-1. 読み保存（いちばん効く）

日本語の同音異義の訂正は、**定義上、読みを変えない**。

```
苦闘店 → 句読点     読み: くとうてん → くとうてん   ✔ 通す
動音域語 → 同音異義語 読み: どうおんいきご → どうおんいぎご ✔ 通す（濁点は許容差分）
```

一方、幻覚・言い換え・要約は**必ず読みを変える**。だから保守モード（文字起こし）では、
**校正前後の読みの一致を要求する**。

- 実装は既にある。`server/reconvert.py` が持つ Sudachi のトークナイザを借りて読みを取る
  （辞書の二重ロードを避けるため `get_tokenizer()` を足した）。新しい依存は要らない。
- **数詞は読みから外す。** Sudachi は「2000」を「にれいれいれい」、「二千」を「にせん」と
  読むので、数詞を読みに含めると**正しい表記換えが言い換えに化ける**（実装して初めて
  分かった。偽の形態素解析では出ない食い違い）。数値の同一性は §5-2 が値として見るので、
  読みの側は数詞ごと落として、それ以外の音だけを比べる。
- 許容する差分は**明示列挙のみ**：句読点・記号の増減、濁点／半濁点、長音と母音、
  送り仮名の正書法、数字表記（にせん↔2000）。それ以外の読みの差は**却下**。
- これで「校正か捏造か」を実行時にほぼ完全に切り分けられる。**取材で使える根拠がここにある。**

口述モードでは緩める。フィラー除去は読みを減らすため一致は要求できない。代わりに
**部分列であること**を要求する：

```
校正後の読み ⊆ 校正前の読み（順序を保った部分列）
```

これで「消す」は通り、「作る」は通らない。言い換え（読みの置換）も通らないので、
文体の整えを許すかは別スイッチにする（§11-2）。

### 5-2. 数字と固有名詞の保存

- 本文中の数値は多重集合として保存する（§5-1 の正書法変換を除く）。会見の「1,200億円」が
  静かに「1,300億円」になる事故は、これで止まる。
- 用語集にない**新しい固有名詞をAIが持ち込んだら却下**する。
  `server/dictcandidates.py` が既に同じ規律を持っている（「**一番危ない失敗**: LLMが正解側に
  無い綴りを作ってくる」）。オフラインで通した検証を、そのままオンラインの門にする。
- ただし**読みが入力にある語は通す**。「スミシン」と聞こえた箇所を「住信」に直すのは、
  音に無いものを作っていない。この一行があるので、用語集に無い誤変換も直せる
  （無いと、辞書に登録済みの語しか直せない道具になってしまう）。

### 5-3. 欠落ガード（既存資産をそのまま使う）

`plugin/refinement.ts` の `assessRefinementSafety()` は、補正稿が速報稿の大部分を捨てて
いないかを LCS カバレッジで判定する。PC音声の30秒補正で既に実績がある。**同じ関数を
AI校正の出力にも掛ける**。先頭欠落・末尾欠落・全体乖離の3種はここで落ちる。

### 5-4. 落ちたときの扱い

- 生テキストを残す。**黙って捨てない、黙って通さない**。
- 却下理由（`reading-changed` / `number-changed` / `invented-term` / `too-short` / …）を
  件数つきで記録する。プロンプトとモデルの良し悪しは、この分布で判断する。
- 却下が続く区間はステータスに出す（無言で効かないのがいちばん困る、というのは
  「⚠ 音が来ていません」で既に学んでいる）。

### 5-5. 人の編集を上書きしない

PC音声の補正が既に守っている規則をそのまま適用する。**差し替え対象を手で編集していた場合は
上書きせず、生（速報）を残す。** `dictated.ts` の範囲追従がこれを成立させている。

## 6. 辞書の役割替え — 置換器から用語集へ

辞書は捨てない。**役割を変える。**

| | 現行 | 新 |
|---|---|---|
| 形 | 無条件の文字列置換 | AIへ渡す**用語集**（文脈で当たる事前分布） |
| 事故 | 正しい語を潰す（要プレビュー機構） | **構造的に起きない**（文脈が見えているため） |
| 登録の重さ | 慎重に（潰す危険がある） | 気楽に（外れても文脈で当たらないだけ） |
| 効く範囲 | 認識のとき＋ノートへの一括適用 | 校正のたび（＝再実行で過去のノートにも効く） |

そして**逆方向が繋がる**。AI校正が直した `(誤り, 正解)` の対は、そのまま登録候補になる。
`dictcandidates.py` が今オフラインでやっていること（要約を正解側に使って候補を作る）が、
**普段の運用の中で自動的に回る**。0.23.0 で作った「登録前に何箇所どう変わるか見せる」画面は、
用語集の追加が置換ではなくなるぶん軽くできる。

なお、**曖昧さのない綴りの誤り**（`SMTV`→`SMTB`、`スミシン`→`住信`）は Stage 2 の
決定的置換に残す。AIに投げる必要がないし、投げないほうが速くて確実。

## 7. 機能の取捨

再設計の価値は、足すものより**捨てられるもの**で決まる。

### 残す

| 機能 | 理由 |
|---|---|
| 録音の保存と再認識（`retranscribe.py`） | 後段を作り直せる土台。今回いちばん効く資産 |
| **言い直し**（選択範囲／語指定） | 音に無い情報はAIでも復元できない。唯一AIで置き換わらない対話機能 |
| 入力キャンセル／復元 | 決定的で速い。AIに委ねる理由がない |
| **入力終了** | 決定的でなければならない。AIの判断に依存させない |
| 辞書 | §6 のとおり用語集として |
| このノートに辞書を当てる | **「このノートにAI校正を掛け直す」へ発展させる**（Phase A がこれ） |
| PC音声の30秒補正 | Stage 3 の差し替え機構がそのまま流用できる |

### 降格（設定の裏へ回し、実測してから消す）

いずれも「同音異義を1件ずつ人が選ぶ」ための機構。AI校正が当たるなら出番が激減する。

- 変換戻し（Google CGI API）
- 再変換／読みの揺らし（`variant_candidates`）
- 叩いて直す（口述範囲のタップ→候補）
- 候補モーダルの「範囲を広げる」

**ただし最終手段を1つは残す。** 推奨は「**選択範囲を再変換**」。AI校正が外した箇所を人が
確実に直す経路は要る。残りは実測（使用回数）を取ってから落とす。
非公式APIへの依存（Google CGI）が消えるのは副次的な利点。

### 見直し

- **音声コマンドのプレフィックス・誤爆対策**：文脈で判断できるようになれば要らなくなる可能性が
  ある。ただし停止系（入力終了）は決定的経路に残すこと。**AIが判断してから止まる停止ボタン**は
  作ってはいけない。
- **形態素ルールの自動句読点**：Stage 3 と重複する。フォールバックとして残す（§4）。

## 8. LLM をどこで動かすか

**既定はローカル。** 「無料・ローカル認識」はこの製品の柱で、取材内容が外へ出ないことが
使える理由そのもの。同じ自宅PCで、日本語の効く 7〜14B 級を量子化して常駐させる。

**GPU競合の扱い**：AI校正を**リアルタイム経路に入れない**。ブロック境界（既定30秒）と
停止時に走らせ、認識のレイテンシ予算には触らせない。PC音声の30秒補正が既に同じ形で
動いているので、体験としても実装としても前例がある。

**クラウドAPIは任意・既定OFF。** 使うなら明示同意のうえで、`dictcandidates.py` が既に
引いている線（「音声は渡さない」）を守る。テキストだけを渡す。

モデルとプロンプトは**ベンチで決める**。`server/bench_en.py` に倣って `bench_refine.py` を置き、
保存済み録音に対して §10 の指標を出す。ここは「良さそう」で決めない。

## 9. 実装の順番

### Phase 0 — 門と計測の道具（**実装済み**）

先に測れるようにした。モデルを選ぶ前に、門と物差しが要るため。詳細は §12。

- `server/refine_guard.py` — 4つの門とモード定義
- `server/refine_llm.py` — Ollama互換の呼び出しと、モードごとのプロンプト
- `server/bench_refine.py` — 保存済みテキスト／録音に対して指標を出すCLI
- `server/test_refine_guard.py`（21件）、`server/test_bench_refine.py`（9件）

### Phase 1 — 測る（**手順は `docs/PHASE1_MEASURE.md`。実行は自宅PC**）

自宅PCにローカルLLMを立て、実際のノートに掛けて §10 の指標を取る。
**ここで採否が決まる。**「悪化しない」ことは門が保証しているので、見るべきは
「効くか」と「いくらかかるか」の2つだけ。

**正解データは作らない。辞書がそのまま正解になる。** 登録済みの `SMTV → SMTB` は
実際に観測された誤認識と正しい表記の対なので、手元のノートに `SMTV` があれば
そこは誤りだと分かっている。評価用の文章を書き起こす必要はない（書き起こすと、
書いた側の想定しか測れない）。`server/refine_score.py` がこれを数える。

**本命の実験は「用語集を渡さずに測る」**（`--no-glossary`）。語を1件ずつ登録しなくても
本文が直るなら、辞書の「モデルに教える」役割は要らなくなる。ただし門の許可証としての
登録は残る（語の門は用語集に無い固有名詞を通さない）ので、**モデルが直した数と、
門を通って本文が直る数を別々に数える**。この差が「辞書は許可証として要る」の大きさになる。

### Phase 2 — 停止後の一括AI校正（原稿執筆モードのみ）

コマンド1つ：**「このノートをAI校正する」**（選択があればその範囲）。

- 読み・数値・語・欠落の4門＋差分表示＋1トランザクション＋`Ctrl+Z` 一回。
  UIは 0.23.0 の「このノートに辞書を当てる」がほぼそのまま使える。
- **リアルタイム経路に一切触らない。** 壊す余地が無く、効果だけ先に測れる。
- これだけで「乱雑に喋って、あとで直す」が成立する。

### Phase 3 — 口述中の自動校正

30秒ブロックごとに校正して速報を差し替える。手編集した箇所は上書きしない。
Stage 2 の自動句読点をフォールバックへ降ろす。

### Phase 4 — 取材モードと対話モード

取材ノートへの適用（生テキストを残したまま表記だけ直す）と、対話モードの追加。
どちらも門は既にあるので、プロンプトと呼び出し口だけ。

### Phase 5 — AI整形と、学習の環

段落・見出し・話者ラベル。校正結果 →(誤り, 正解) 対 → 用語集の登録候補。
降格した対話機構の使用実測を取り、消す。

## 10. 評価 — これが無いなら入れない

保存済み録音と取材ノートを回帰コーパスにする（会見・インタビュー・取材・発表会が既に揃っている）。
**残存誤変換以外は、正解データ無しで自動で取れる**ように作った。

| 指標 | 取り方 | 判断 |
|---|---|---|
| 残存誤変換／千字 | 人手（`--diff` の一覧を見る） | 下がること |
| **読み保存違反率** | 機械 | 取材モードで **0%** |
| **幻覚件数**（持ち込まれた数値・語） | 機械 | 取材モードで **0件** |
| 却下率と内訳 | 機械 | プロンプト／モデル比較の主指標 |
| **直した量（字／ブロック）** | 機械 | **0 なら不採用** |
| 所要時間／ブロック | 機械 | 認識のレイテンシに影響しないこと |

**直した量を必ず見ること。** 何もしないモデルは全部の門を通るので、通過率だけを見ると
最優秀に見える（`--model stub` がまさにそれ。ベンチはこの場合に警告を出す）。
「安全」と「有用」は別の指標で、両方見ないと選べない。

**採用基準を先に決めておく**：誤変換が半分になっても、**捏造が1件でも通るモデルは
取材モードでは採用しない**。口述専用として別途採用するのは可。

### リスク

- **ローカル7B級の日本語校正が、同音異義の選択で人間以下**の可能性。→ 門で「悪化」は
  防げるが「効かない」は防げない。Phase 1 で先に測るのはこのため。
- **テキストが後から書き換わる体験**の落ち着かなさ。→ Phase 2 が停止後の明示起動なのは
  これも理由。自動化は Phase 3 で、効くと分かってから。
- **GPU競合と VRAM**。→ 非リアルタイム経路に置く。足りなければ停止後のみ。
- **句読点をAIに任せると、形態素ルールの最低線を割る**可能性。→ フォールバックを残す。

## 11. 決定と、残っている判断

### 決めたこと（2026-08-28）

| 問い | 答え |
|---|---|
| ローカルLLM既定でよいか | **実測してから決める。** 道具を先に作った（§12） |
| 口述でどこまで許すか | **原稿執筆モード**（フィラー除去・整形あり）と**対話モード**（表記の訂正のみ）に分ける。**まず原稿執筆モードのみ** |
| 降格した対話機構をいつ消すか | **実測の結果を見てから** |
| 取材ノートで正となるのは | **生テキスト。** ただし表記は直す（取材モードの門で、読みが変わらないことを保証する） |

### 残っている判断（測ってから）

1. **モデルとサイズ。** 7B / 14B / それ以上。速度と精度の折れ点はどこか。
2. **対話モードを作るか。** 原稿執筆モードのコストを見てから。
3. **クラウドAPIを選択肢に持つか。** ローカルで足りるなら、持たないほうが仕様は小さい。
4. **ブロック長。** 既定400字。長いと要約に倒れ、短いと文脈が足りず同音異義を直せない。

## 12. 計測の道具（実装済み）

```powershell
cd server

# まず配線の確認（モデル不要。全部通って「直した量0」になるのが正しい）
.\.venv\Scripts\python.exe bench_refine.py --text ノート.md --model stub

# ローカルモデルで測る（既定 http://localhost:11434 の Ollama 互換）
.\.venv\Scripts\python.exe bench_refine.py --text 会見.md --mode manuscript --model qwen3:8b -v

# モデルを並べて比べる
.\.venv\Scripts\python.exe bench_refine.py --text 会見.md --compare qwen3:8b qwen3:14b gemma3:12b

# 校正後の本文と、変更箇所の一覧を書き出す（残存誤変換はこの一覧で数える）
.\.venv\Scripts\python.exe bench_refine.py --text 会見.md --model qwen3:8b --out 校正後.md --diff 変更.md

# 用語集（辞書の正解表記）を渡す
.\.venv\Scripts\python.exe bench_refine.py --text 会見.md --model qwen3:8b --dictionary-set default

# 保存済み録音から生テキストを作り直して測る（GPUが要る）
.\.venv\Scripts\python.exe bench_refine.py --session 20260806-133113 --limit-sec 600 --model qwen3:8b

# 門のテスト
.\.venv\Scripts\python.exe test_refine_guard.py
.\.venv\Scripts\python.exe test_bench_refine.py
```

**口述の録音は残らない**（`recording.py` は文字起こしモードだけ）。原稿執筆モードの
コーパスは、当面は**会見・取材の生テキスト**で代用する。自然発話でフィラーも言い直しも
入っているので、入力の性質としては近い。厳密に測りたくなったら、口述の録音を
（明示的に有効にしたときだけ）残す仕組みを足す。

**Sudachi が無ければ校正しない。** 読みの門が動かないまま通すのは、門が無いのと同じで、
しかも「あるように見える」ぶん危ない。ベンチは終了コード2で止まる。
