# VoxCraft 再設計案 — 認識で当てにいくのをやめる

作成: 2026-08-28 / 対象: `0.23.0` 以降 / 種別: 仕様検討（実装前）

仕様と機能をもう一度一から検討した結果をまとめる。結論・その理由・**捨てるものの一覧**まで書く。
実装計画は §9、決めてほしいことは §11。

---

## 1. 診断 — なぜ満足に届かないのか

現行には、明文化されていない前提が2つある。

1. 認識結果が本文に落ちた時点で、ほぼ正しい。
2. 残った誤りは**1件ずつ、その場で、対話的に**直す。

0.10 から 0.23 までの開発は、ほぼ全部この2番めを強くする作業だった。再変換、読みの揺らし、
叩いて直す、範囲を広げる、言い直し、辞書のクイック登録、ノートへの辞書適用。
どれも良くできているが、前提そのものに4つの限界がある。

### 1-1. 修理コストが誤り1件ごとに掛かり、思考を中断する

READMEには「**誤変換・誤認識を直す（どれを使うか）**」という表がある。利用者は誤りを見つけた
うえで、さらに「読みは合っているか」「読みごと壊れているか」「英字か」を**分類してから**
道具を選ぶ。これは認識器の内部事情がそのまま操作に出ている状態で、口述の目的（考えを止めずに
書く）と正面から衝突する。1件あたり数秒でも、文章を書く速度を決めているのは操作時間ではなく
**中断の回数**のほう。

### 1-2. 認識の天井は、対話では破れない

0.20.3 で自分たちで測ったとおり。

> 読みは どうおんい**き**ご で、正しい どうおんい**ぎ**ご とは濁点1つ違い。濁点の有無は音として
> 小さく、モデルの言語的な事前分布のほうが強い。**同じ言葉をはっきり言い直しても結果は動かない**。

ここが本質。**音をもう一度入れても越えられない壁**があり、それを越えるのに要るのは
より良いマイクでも大きいモデルでもなく、**前後の文脈を持った別の判断**である。
現行はその判断を全部「人間の目と指」に割り当てている。

### 1-3. 辞書は片方向のラチェットで、しかも破壊的

辞書は無条件置換なので、危ないのは**誤りを直すつもりで正しい語を潰す**登録だった
（0.23.0：「マイナカード」を登録すると本文の「マイナンバーカード」29箇所が消える）。
そのためにプレビュー機構・省略判定・件数の数え方まで作り込んだ。よく効いているが、
**事故を防ぐ機構が必要になる時点で、道具の形が用途に合っていない**。
「この語はこの分野ではこう書く」は本来、文脈を見て適用する知識であって、全文一括置換ではない。

### 1-4. 正しく認識できても、話し言葉は文章ではない

ここが、たぶん「満足いかない」の最大の成分。

フィラー（えー、あの）、言い直し（〜じゃなくて〜）、助詞の崩れ、係り受けの飛び、
文の切れ目の曖昧さ、段落なし。**認識精度が100%でも残る**問題で、現行はここにほとんど
何も持っていない。句読点は形態素ルール（README自ら「Google日本語入力ほどの精度ではない」）、
段落は文字数と間の閾値。見出し・箇条書き・話者ラベルは無い。

つまり現行は「認識精度」の問題を解き続けてきたが、**残っている不満の大半は
「認識のあとの工程が存在しない」ことに由来する**。

## 2. 設計原理の入れ替え

一行で書く。

> **音は音でしか決まらないことだけ決めさせ、文脈が要る判断は文脈を持つモデルへ渡す。**

判断ごとに、必要な情報と担当を置き直すと、現行のねじれが見える。

| 判断 | 決めるのに要る情報 | 現行の担当 | 新しい担当 |
|---|---|---|---|
| 音素・語彙の書き起こし | 音声 | Whisper | **Whisper（変えない）** |
| 同音異義語の選択 | 前後の文脈・話題 | 人（叩く→候補→選ぶ） | **AI校正** |
| 固有名詞・専門用語の表記 | 分野知識・用語集 | 辞書（無条件置換） | **AI校正**（用語集を事前分布として） |
| 句読点 | 統語 | 形態素ルール | **AI校正** |
| 段落・見出し・箇条書き | 談話構造 | 文字数と間 | **AI整形** |
| フィラー・言い直しの整理 | 話者の意図 | なし（人手） | **AI校正**（口述モードのみ） |
| 読みごと壊れた誤認識 | **新しい音** | 言い直し | **言い直し（残す）** |

最後の行が要点。**AIで置き換えられない対話機能はこれ1つだけ**である。音に入っていない情報は
どんなモデルでも復元できないので、そこだけは人がもう一度喋るしかない。逆に言えば、
それ以外の対話機構は、原理的にAI側へ寄せられる。

利用者から見た変化は、機能の増加ではなく**覚えることの減少**になる。

- 誤りの種類を分類しなくていい（道具の選択表が要らない）。
- 誤りを見つけるために手を止めなくていい（見つける前に直っている）。
- 辞書を育てなくても、今日のノートがその日のうちに読める。

## 3. 二つのモードは、二つの製品である

現行は口述と文字起こしを1つの後処理で扱っている。ここを**分ける**。分ける軸は速度でも
遅延でもなく、**忠実性が要るかどうか**。

| | 口述（自分の文章を書く） | 文字起こし（他人の発話・引用が要る） |
|---|---|---|
| 著者 | 自分 | 話した本人 |
| 一字一句 | 変えてよい | **根拠。変えてはいけない** |
| AI校正の権限 | 表記の訂正＋フィラー除去＋文体の整え | **表記の正規化まで**（同音異義・固有名詞・句読点） |
| AI整形 | 既定ON | 既定OFF（明示起動のみ） |
| 言い換え・要約 | 別コマンドとして可 | **禁止** |
| 正となるテキスト | 校正稿 | **生テキスト**（校正稿は表示・作業用） |

取材で使う以上、「AIが良かれと思って言い回しを整えた引用」は**成果物として使えない**。
禁止をプロンプトで頼むのではなく、§5 の検証で機械的に落とす。

## 4. 新しいパイプライン

```
  音声
   │
   ├─ Stage 0  取り込み        VAD / ノイズ減算 / 連結 / 言語判定      ← 据え置き
   │
   ├─ Stage 1  認識            Whisper → 生テキスト(raw)              ← 据え置き
   │                            ★ raw は音声と対で永久に残す
   │
   ├─ Stage 2  決定的後処理     和欧スペース / 記号語 / 明示コマンド    ← 縮小
   │                            / 曖昧さのない綴り置換のみ
   │
   ├─ Stage 3  AI校正 (新)      同音異義・固有名詞・句読点
   │                            (口述のみ) フィラー・言い直しの整理
   │                            → 検証 → 差分 → 差し替え
   │
   └─ Stage 4  AI整形 (新・任意) 段落 / 見出し / 箇条書き / 話者ラベル
```

**Stage 0 は触らない。** 実測で最適点に置いてあり（連結10秒、減算の強さをSNRで決める、
言語判定は base + 確信度0.75）、この提案はそこを一切変えない。

**Stage 2 を縮小する。** 今そこにある2つを外へ出す。

- **辞書の無条件置換** → 曖昧さのないもの（`SMTV`→`SMTB` のような綴りの誤り）だけ残す。
  読みとして曖昧なキーは Stage 3 の用語集へ移す。分ける基準は「キーが読みとして一意か」。
- **形態素ルールの自動句読点** → Stage 3 がある時は不要。ただし AI校正が落ちた／却下された
  ときのフォールバックとして残す（削除しない）。

**契約（重要）**

- Stage 1 の出力は不変。Stage 3 以降は**必ず raw から再計算できる**。
  → プロンプトやモデルを変えたら、保存済み録音に対して**認識をやり直さずに**
    校正だけ回し直せる（`retranscribe.py` の思想を、後段だけに適用する）。
- Stage 3/4 は**べき等**。同じ raw ＋同じ用語集＋同じモデルなら同じ結果に落ちる
  （温度0、決め打ちの分割）。
- Stage 3/4 が触ってよいのは、**口述範囲として記録されている箇所だけ**
  （`plugin/dictated.ts` が既に持っている。手で書き換えた箇所は範囲から自動的に外れる）。

## 5. AI校正の安全性仕様 — この提案の核心

プロンプトに「勝手に書き換えるな」と書くのは仕様ではない。**機械で落とせる不変条件**を置く。

### 5-1. 読み保存（いちばん効く）

日本語の同音異義の訂正は、**定義上、読みを変えない**。

```
苦闘店 → 句読点     読み: くとうてん → くとうてん   ✔ 通す
動音域語 → 同音異義語 読み: どうおんいきご → どうおんいぎご ✔ 通す（濁点は許容差分）
```

一方、幻覚・言い換え・要約は**必ず読みを変える**。だから保守モード（文字起こし）では、
**校正前後の読みの一致を要求する**。

- 実装は既にある。`server/reconvert.py` の `_Reading.to_hiragana()` が任意テキストの
  ひらがな読みを返す（Sudachi）。新しい依存は要らない。
- 許容する差分は**明示列挙のみ**：句読点・記号の増減、濁点／半濁点、長音と母音、
  送り仮名の正書法、数字表記（にせん↔2000）。それ以外の読みの差は**却下**。
- これで「校正か捏造か」を実行時にほぼ完全に切り分けられる。**取材で使える根拠がここにある。**

口述モードでは緩める。フィラー除去は読みを減らすため一致は要求できない。代わりに
**部分列であること**を要求する：

```
校正後の読み ⊆ 校正前の読み（順序を保った部分列）
```

これで「消す」は通り、「作る」は通らない。言い換え（読みの置換）も通らないので、
文体の整えを許すかは別スイッチにする（§11-2）。

### 5-2. 数字と固有名詞の保存

- 本文中の数値は多重集合として保存する（§5-1 の正書法変換を除く）。会見の「1,200億円」が
  静かに「1,300億円」になる事故は、これで止まる。
- 用語集にない**新しい固有名詞をAIが持ち込んだら却下**する。
  `server/dictcandidates.py` が既に同じ規律を持っている（「**一番危ない失敗**: LLMが正解側に
  無い綴りを作ってくる」）。オフラインで通した検証を、そのままオンラインの門にする。

### 5-3. 欠落ガード（既存資産をそのまま使う）

`plugin/refinement.ts` の `assessRefinementSafety()` は、補正稿が速報稿の大部分を捨てて
いないかを LCS カバレッジで判定する。PC音声の30秒補正で既に実績がある。**同じ関数を
AI校正の出力にも掛ける**。先頭欠落・末尾欠落・全体乖離の3種はここで落ちる。

### 5-4. 落ちたときの扱い

- 生テキストを残す。**黙って捨てない、黙って通さない**。
- 却下理由（`reading-changed` / `number-changed` / `invented-term` / `too-short` / …）を
  件数つきで記録する。プロンプトとモデルの良し悪しは、この分布で判断する。
- 却下が続く区間はステータスに出す（無言で効かないのがいちばん困る、というのは
  「⚠ 音が来ていません」で既に学んでいる）。

### 5-5. 人の編集を上書きしない

PC音声の補正が既に守っている規則をそのまま適用する。**差し替え対象を手で編集していた場合は
上書きせず、生（速報）を残す。** `dictated.ts` の範囲追従がこれを成立させている。

## 6. 辞書の役割替え — 置換器から用語集へ

辞書は捨てない。**役割を変える。**

| | 現行 | 新 |
|---|---|---|
| 形 | 無条件の文字列置換 | AIへ渡す**用語集**（文脈で当たる事前分布） |
| 事故 | 正しい語を潰す（要プレビュー機構） | **構造的に起きない**（文脈が見えているため） |
| 登録の重さ | 慎重に（潰す危険がある） | 気楽に（外れても文脈で当たらないだけ） |
| 効く範囲 | 認識のとき＋ノートへの一括適用 | 校正のたび（＝再実行で過去のノートにも効く） |

そして**逆方向が繋がる**。AI校正が直した `(誤り, 正解)` の対は、そのまま登録候補になる。
`dictcandidates.py` が今オフラインでやっていること（要約を正解側に使って候補を作る）が、
**普段の運用の中で自動的に回る**。0.23.0 で作った「登録前に何箇所どう変わるか見せる」画面は、
用語集の追加が置換ではなくなるぶん軽くできる。

なお、**曖昧さのない綴りの誤り**（`SMTV`→`SMTB`、`スミシン`→`住信`）は Stage 2 の
決定的置換に残す。AIに投げる必要がないし、投げないほうが速くて確実。

## 7. 機能の取捨

再設計の価値は、足すものより**捨てられるもの**で決まる。

### 残す

| 機能 | 理由 |
|---|---|
| 録音の保存と再認識（`retranscribe.py`） | 後段を作り直せる土台。今回いちばん効く資産 |
| **言い直し**（選択範囲／語指定） | 音に無い情報はAIでも復元できない。唯一AIで置き換わらない対話機能 |
| 入力キャンセル／復元 | 決定的で速い。AIに委ねる理由がない |
| **入力終了** | 決定的でなければならない。AIの判断に依存させない |
| 辞書 | §6 のとおり用語集として |
| このノートに辞書を当てる | **「このノートにAI校正を掛け直す」へ発展させる**（Phase A がこれ） |
| PC音声の30秒補正 | Stage 3 の差し替え機構がそのまま流用できる |

### 降格（設定の裏へ回し、実測してから消す）

いずれも「同音異義を1件ずつ人が選ぶ」ための機構。AI校正が当たるなら出番が激減する。

- 変換戻し（Google CGI API）
- 再変換／読みの揺らし（`variant_candidates`）
- 叩いて直す（口述範囲のタップ→候補）
- 候補モーダルの「範囲を広げる」

**ただし最終手段を1つは残す。** 推奨は「**選択範囲を再変換**」。AI校正が外した箇所を人が
確実に直す経路は要る。残りは実測（使用回数）を取ってから落とす。
非公式APIへの依存（Google CGI）が消えるのは副次的な利点。

### 見直し

- **音声コマンドのプレフィックス・誤爆対策**：文脈で判断できるようになれば要らなくなる可能性が
  ある。ただし停止系（入力終了）は決定的経路に残すこと。**AIが判断してから止まる停止ボタン**は
  作ってはいけない。
- **形態素ルールの自動句読点**：Stage 3 と重複する。フォールバックとして残す（§4）。

## 8. LLM をどこで動かすか

**既定はローカル。** 「無料・ローカル認識」はこの製品の柱で、取材内容が外へ出ないことが
使える理由そのもの。同じ自宅PCで、日本語の効く 7〜14B 級を量子化して常駐させる。

**GPU競合の扱い**：AI校正を**リアルタイム経路に入れない**。ブロック境界（既定30秒）と
停止時に走らせ、認識のレイテンシ予算には触らせない。PC音声の30秒補正が既に同じ形で
動いているので、体験としても実装としても前例がある。

**クラウドAPIは任意・既定OFF。** 使うなら明示同意のうえで、`dictcandidates.py` が既に
引いている線（「音声は渡さない」）を守る。テキストだけを渡す。

モデルとプロンプトは**ベンチで決める**。`server/bench_en.py` に倣って `bench_refine.py` を置き、
保存済み録音に対して §10 の指標を出す。ここは「良さそう」で決めない。

## 9. 実装の順番

### Phase A — 停止後の一括AI校正（最小・いちばん効く）

コマンド1つ：**「このノートをAI校正する」**（選択があればその範囲）。保守モード固定。

- 読み保存ガード＋欠落ガード＋差分表示＋1トランザクション＋`Ctrl+Z` 一回。
  UIは 0.23.0 の「このノートに辞書を当てる」がほぼそのまま使える。
- **リアルタイム経路に一切触らない。** 壊す余地が無く、効果だけ先に測れる。
- これだけで「乱雑に喋って、あとで直す」が成立する。**まずここまでを作る。**

### Phase B — 口述中の自動校正

30秒ブロックごとに校正して速報を差し替える。手編集した箇所は上書きしない。
Stage 2 の自動句読点をフォールバックへ降ろす。

### Phase C — AI整形

段落・見出し・箇条書き・話者ラベル。口述は既定ON、文字起こしは既定OFF・明示起動。

### Phase D — 学習の環を閉じる

校正結果 →(誤り, 正解) 対 → 用語集の登録候補。降格した対話機構の使用実測を取り、消す。

## 10. 評価 — これが無いなら入れない

この repo の作法どおり、**実測なしでは採用しない**。保存済み録音を回帰コーパスにする
（会見・インタビュー・取材・発表会が既に揃っている）。

| 指標 | 取り方 | 判断 |
|---|---|---|
| 残存誤変換／千字 | 人手カウント | 下がること |
| **読み保存違反率** | 機械（§5-1） | 保守モードで **0%** |
| **幻覚件数**（追加された固有名詞・数字） | 機械（§5-2） | 保守モードで **0件** |
| 却下率と内訳 | 機械 | プロンプト／モデル比較の主指標 |
| 校正の所要時間／ブロック | 機械 | 認識のレイテンシに影響しないこと |
| 人手修正の回数／分 | 運用ログ | 下がること（本来の目的） |

**採用基準を先に決めておく**：誤変換が半分になっても、**捏造が1件でも通るモデルは採用しない**。
取材に使えなくなるため。口述専用として別途採用するのは可。

## 11. リスクと、決めてほしいこと

### リスク

- **ローカル7B級の日本語校正が、同音異義の選択で人間以下**の可能性。→ §5 のガードで
  「悪化」は防げるが「効かない」は防げない。Phase A で先に測るのはこのため。
- **テキストが後から書き換わる体験**の落ち着かなさ。→ 口述は自動、文字起こしは手動起動、が妥当。
- **GPU競合とVRAM**。→ 非リアルタイム経路に置く（§8）。それでも足りなければ校正は停止後のみ。
- **句読点をAIに任せると、形態素ルールで担保していた最低線を割る**可能性。→ フォールバックを残す。

### 決めてほしいこと

1. **ローカルLLM既定でよいか。** クラウドAPIを選択肢として持つか、最初から持たないか。
2. **口述モードでどこまで許すか。** 表記の訂正だけか、フィラー除去まで許すか、文体の整えまで
   許すか。「話したまま残したい」なら §5-1 の部分列条件も外す設定が要る。
3. **降格した対話機構をいつ消すか。** Phase A の結果を見てからでよいか。
4. **取材ノートで正となるのはどちらか。** 本案は「生テキストが正、校正稿は表示・作業用」を
   既定に置いている（引用の検証は音と生テキストで行う）。これでよいか。
